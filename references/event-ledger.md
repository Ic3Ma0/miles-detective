# 事件台账、下一轮计划与预算

这份参考把「人物调查」从一堆结论整理成可合并的事件链。事件多、跨轮续查、同一件事被多家媒体报道时使用；小案例可以只用结论和线索。

## 什么时候建事件台账

材料覆盖 **≥5 年**，或预计 **≥10 个可定位事件**，或属于**续轮/合并**时，默认建事件台账。低于这个规模，可以只用结论、线索和简短时间线。达到阈值却不建，等于把事件留给叙事记忆，下一轮无法合并、也无法发现覆盖空白。

- 人物跨越多个阶段，事件需要按时间排列。
- 同一件事被多家媒体、多次转载或本人多次回忆。
- 需要跨轮合并，避免每一轮都把旧事件重新算一遍。
- 写作时需要从事件里挑场景，而不是从结论列表里硬凑。

结论（claim）回答「材料这样记载了什么」；事件（event）回答「什么时候、在哪里、谁做了什么、后来怎样」。两者互相引用，不互相替代。

## 事件字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `EV01` 这类稳定编号；更新同一事件时复用 |
| `date` | 否 | 尽量写到日；未知时留空 |
| `date_precision` | 是 | `day` / `month` / `year` / `range` / `unknown` |
| `scope` | 是 | `main` / `background` / `outside_window`；前史与窗外材料不混入主时间线 |
| `evidence_type` | 是 | `self_account` / `journalist_report` / `institution_record` / `mixed` / `unknown` |
| `title` | 是 | 一句话事件名，不写评价 |
| `summary` | 是 | 实际发生了什么；不写心理动机 |
| `place` | 否 | 有材料支持才写 |
| `people` | 否 | 在场或直接相关的公开人物 |
| `consequence` | 否 | 有来源的后续；不把时间先后当因果 |
| `status` | 是 | `documented` / `corroborated` / `disputed` / `unverified` |
| `source_ids` | 否 | 对应 `records.jsonl` 的来源编号 |
| `claim_ids` | 否 | 对应结论编号 |
| `sources` | 否 | 案头核读用的文件定位：`[{"file":"V01.txt","lines":"12"}]`、`[{"id":"V29","lines":"12"}]` 或 `[{"source_id":"S03","lines":"11-30"}]` |
| `same_event_group` | 否 | 同一事件的不同报道共用一个组名 |
| `date_note` | 否 | 日期冲突或存疑时写清两种说法 |

`source_ids`、`claim_ids`、`sources` 至少要有一个；不能只凭搜索摘要建事件。`scope` 与 `evidence_type` 让读者分清「主窗口/前史/窗外」和「本人自述/记者报道/机构记录」，不能只靠 `status` 一个字段承担全部信息。

示例：

```json
{"kind":"event","id":"EV01","date":"2001-06-11","date_precision":"day",
 "scope":"main","evidence_type":"journalist_report",
 "title":"CNNIC 办公室会面","summary":"毛伟提出八条合作条件，双方开始六次面谈。",
 "place":"北京中关村","people":["周鸿祎","毛伟"],"status":"documented",
 "source_ids":["S03"],"claim_ids":["C11"],"same_event_group":"cnnic-2001",
 "sources":[{"source_id":"S03","lines":"11-30"}]}
```

把事件和它引用的来源、结论放在同一批 `append` 里，被引用的记录必须先出现；`report` 会把最新事件快照输出成时间线。事件编号用 `EV01` 这类稳定值，改标题或补后续时复用同一个 `id`。如果事件单独存成 `events.json`，交付前运行 `python3 <技能目录>/scripts/check_events.py events.json`；它会检查必填字段、`scope`/`evidence_type`、文件定位，以及 `corroborated` 的同组来源。

## 合并与去重

- **同一事件的判据是时间窗、地点、在场者、行动，不是标题相似。** 标题不同但指向同一次会面，可以合并；标题相同但发生在不同年份，不能合并。
- **转载不是新事件。** 同一稿件的多家转载、同一采访的全文/剪辑/翻译，共用一个 `same_event_group`，事件只建一条，来源列多个。
- **日期冲突先保留。** 在 `date_note` 写两种说法及其来源；能对齐到同一时间窗再合并，不能对齐就分列，不静默选一个。
- **更新事件用同一 `id` 追加新记录。** 改标题、补后续、升级状态都保留历史；`report` 使用最新快照。
- **状态升级要补来源组。** 从 `documented` 升到 `corroborated`，必须按四问核对独立性，不能因为又多了一个转载就升级。每个被引来源要写 `same_source_group`；两个来源同组（同一家 TorrentFreak、同一公告的转述）不能标；文件定位要写 `group`。只有两个不同来源组才算独立。
- **同一日不同行动可以分列。** 同一天「拍下午餐、发公开信、与第三方互怼」是三个行动，不必合成一条；同一行动的多篇报道才合并。判据仍是时间窗、地点、在场者、行动，不是日期本身。
- **跨分片合并先跑脚本。** 并行调查用 `research_log.py merge` 把分片台账合成主台账；脚本只自动合并明确标了同一 `same_event_group` 的事件，日期、地点或标题相同但未标组的事件只列为重复候选，仍由协调者按时间窗、地点、在场者、行动判断。合并后 `corroborated` 会按同源组重算；被降级的事件、未裁决的冲突要进附卷或下一轮计划。

时间线按 `date` 排序，`unknown` 放最后；`range` 用可读写法（如 `2001-06 至 2001-07`）。

事件台账不单独存年龄；时间线或报告需要年龄列时，按人物出生日期与事件日期换算，出生日期及其精度写在案例范围或姓名索引，只有年份/月份的条目注明近似。

## 从事件到叙事

写作时先选事件，再选场景：事件提供时间、地点、行动、回应和后果；场景需要材料里有具体物件、动作或原话。事件没有的天气、表情、内心独白不补写。事件之间的空白，回到线索队列，不用过渡句填平。

## 下一轮查询计划

每轮结束前，把新发现转成下一轮可执行的查询，而不是只写「继续查」。至少为每个高优先级缺口写一行：

| 缺口 | 为什么重要 | 下一轮查询 | 来源家族 | 成功标准 | 停止条件 |
|---|---|---|---|---|---|
| 例：离开 A 公司到创办 B 公司之间的两年 | 影响对转折的理解 | `"姓名" "A 公司" 离职`；`"姓名" "B 公司" 创办`；旧域名/旧账号 | 同期报道、旧博客、播客 | 找到同期原件或本人明确自述 | 两轮只有同源转载 |

六列必填，停止条件不能省。把同一组数据写进 `delivery.json` 的 `next_plans`，运行 `check_delivery.py`；报告开头的广度/深度预算与停止原因也要与 `delivery.json` 一致。

优先级顺序：缺失的人生阶段 → 关键事件的后续 → 互相矛盾的证据 → 账号与旧内容 → 热门新闻的更多转述。最后一项通常不值得再加一轮。

把本轮学到的东西变成查询变体：新发现的姓名异体、准确标题、旧域名、事件短语、附件名、日期范围。只换形容词搜同一类新闻，不算下一轮计划。

## 预算与停止

开始前在案例范围里写清两件事：

- **广度**：计划覆盖哪些阶段和来源家族。
- **深度**：每个高优先级线索最多追几轮、允许哪些替代入口。

到达预算、或高价值线索已处理且新一轮主要产生同源重复时，交付并保留开放队列。不要因为「还能再搜」就静默扩张；范围明显变大时先问用户。单点追查可以借鉴 Jina 的循环：围绕一个明确问题搜索、阅读、推理、再搜索，直到回答或预算用尽，然后记录失败层级。

## 四道工序（借鉴 GPT Researcher 的分工）

1. **规划**：定阶段、来源家族、预算和高优先级缺口。
2. **取证**：只收集来源、访问、结论和事件，不写故事。
3. **核验**：查语义方向、同源组、日期、`corroborated` 条件和状态同步。
4. **写作**：从已核验事件里选场景，写完再跑交付前检查。

不要在取证阶段边搜边写；写作阶段也不要偷偷补搜。需要补查时回到取证，补完再重写相关段落。

## 不借鉴的部分

多智能体编排、固定的 Tavily/Firecrawl 依赖、通用报告模板不进入本技能。它们是框架选择，不是人物调查方法；本技能保持工具无关、单技能可运行，把「事件—来源—缺口」留在可核查的台账里。
