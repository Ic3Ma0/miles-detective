# 并行调查

当一次联网调查达到阈值、且当前环境支持委派时，把发现与核验按来源家族拆成若干调查分片，由协调者合并。写作、合并总卷与最终语义检查始终单线程。环境不支持委派时，按同一分片计划顺序执行；分片契约不变。

## 何时启用

三条同时满足才分片：

- 模式是联网调查，不是案头核读；
- 材料预计覆盖 ≥5 年，或预计 ≥10 个可定位事件；
- 当前环境支持委派，或用户明确要求拆分执行。

默认 3 个 worker，最多 4 个。案头核读、小案例、以及主要靠单一来源家族的调查继续单线程。

## 角色

**协调者**（主线程）负责：

- 先建立身份与年代索引，再生成分片计划；身份索引不并行；
- 写全局预算、总截止与每个分片的停止条件；
- 派发分片、接收分片包；
- 运行 `research_log.py merge`，裁决合并冲突；
- 写作、语义检查、最终交付；只有协调者能宣布「本轮可以交付」。

**worker** 负责一个来源家族内的发现、访问、核验与落盘。worker 不写人生故事，不修改主台账，不替其他分片下结论，也不自行宣布整轮完成。

## 分片计划

默认按来源家族切分：本人署名与发言、新闻与特稿、论坛与旧社区、机构记录、播客与视频、著作与出版。每个分片覆盖全时段。单个家族过大时，才按年代二次切分，并在分片名里写清范围。

分片之间不重叠；同一事件被多个家族报道是正常冗余，交给合并与事件台账去重。

## 分片契约

每个分片目录 `shards/<分片 ID>/` 必须包含：

| 文件 | 内容 |
|---|---|
| `shard.json` | 分片 ID、来源家族、范围、身份线索、预算、停止条件、状态、起止时间 |
| `records.jsonl` | 与主台账同结构的检索、访问、来源、结论、事件、线索、覆盖记录 |
| `raw/` | 工具原始返回，按批次保存 |
| `findings.md` | 候选事件、冲突、受阻线索、下一步；不写叙事正文 |

`shard.json` 示例：

```json
{
  "id": "s01-news",
  "family": "新闻与特稿",
  "scope": "1980—2026，含转载、更正与撤稿",
  "identity_index": ["姓名变体与已证实网名"],
  "budget": {"breadth": "覆盖该家族的主要媒体与年代", "depth": "每个高优先级线索最多追两轮"},
  "stop_reason": "主要媒体与年代已检查，新检索只产生同源转载",
  "status": "complete",
  "started_at": "2026-11-02T10:00:00+08:00",
  "ended_at": "2026-11-02T10:40:00+08:00"
}
```

如果运行环境禁止 worker 写 Markdown，worker 在回传报告里交 `findings.md` 的内容，由协调者落盘并在 `shard.json` 注明；不能因此省略候选事件、冲突、受阻线索与下一步。

分片记录里的 `raw_path` 相对分片目录；合并时会改写成 `shards/<分片 ID>/raw/...`。

`findings.md` 使用下面的短模板；各项引用本分片台账 ID，协调者汇总时保留分片 ID，合并后按合并报告映射到主台账。没有的项写“无”，不能为了填模板创造发现或线索。它是交接索引，不另存一套事实或复制原文：

| 类别 | 发现或问题 | 台账关联 | 对人物经历理解的影响 | 建议动作 |
|---|---|---|---|---|
| 重要发现 | 已取得材料支持的经历，保留自述等归属 | 事件 EV… / 结论 C…；来源 S… | 补足哪个阶段或改变哪个转折的理解 | 纳入核读或继续查证 |
| 矛盾 | 尚未裁决的不同说法 | 对应事件、结论及来源 ID | 可能改变什么理解 | 查哪份原件或保留两说 |
| 待追线索 | 尚未获得支持的问题 | 线索 L…，其 origin_ids 指向已有记录 | 为什么值得继续 | 优先级、具体查询、成功标准与停止条件 |
| 受阻项 | 实际读取失败或证据缺口 | 访问 V… / 线索 L… | 哪部分仍不可知 | 公开替代入口或留待续查 |

## 调查中途的追查循环

1. 分片交回阶段发现后，协调者核读关联材料与台账，区分有依据的发现、矛盾和待查问题；不以摘要代替证据。
2. 复用现有 `clue` 的 `origin_ids`、`priority`、`state`、`question` 和 `next_step` 更新调查队列，按对人物理解的价值与剩余时间选择下一步。新线索落在原分片范围内时由该 worker 追加记录；协调者不与 worker 同写分片台账。
3. 在全局调查截止前，可让原 worker 沿高价值线索继续查，或在其停止后释放的并发槽位派发范围不重叠的新分片。任务写明查询、成功标准、停止条件及原有全局截止，不因新任务重置预算。顺序执行时沿用同一循环。
4. 线索已回答、只剩同源重复、受阻且无可用入口，或调查预算耗尽时停止该支线；在已有线索和分片停止原因中记录结果。未解决的高价值缺口进入交付与下一轮计划。

中途协调依靠已交回的记录与摘要，不对仍在写入的分片运行 `merge`。最终合并前先让全部 worker 停止写入并交回稳定分片包，再统一合并、核验与裁决。不要用 `merge --force` 覆盖协调者已追加的主台账；合并后的协调者更正保留在主台账，后续接续时不得重建覆盖。

## 预算与停止

默认时间预算见 `SKILL.md` 的“开始与续查”；所有分片共享调查截止，核对与写作时间不再用于派发搜索。全局广度、深度与总截止写在交付头。协调者按预期价值预分预算，不平均分：本人原文与机构记录优先，聚合页与转载次要。

每个分片有自己的停止条件；worker 只能报告「本片到达停止条件」，不能宣布整轮完成。某个分片提前耗尽且其他支线仍未完成时，协调者可以把余量转给未完成支线，并在 `delivery.json` 记录重新分配。

## 合并

```bash
python3 <技能目录>/scripts/research_log.py merge <案例目录>
```

合并命令只做机械工作：

- 先按分片目录逐个校验分片台账；
- 统一编号，保留 `shard_id` 与原 ID 映射；
- 相同 URL 的来源条目合并为一条，访问层级取较完整者，访问与发现引用取并集；
- `same_source_group` 加上分片前缀，避免不同分片的同名组被误判为同源；
- 按 `same_event_group` 合并明确标记为同一事件的事件；日期、地点或标题相同但未标组的事件只列为重复候选，不自动合并；
- 把日期与在场者的分歧写进 `merge-report.json`，不静默选一个；
- 合并后按同源组重新计算 `corroborated`：不足两个独立来源或两个不同组的，降为 `documented` 并记录原因。

`same_event_group` 只用于「同一事件的多次报道」，不是故事线分组。把宣布、预售、发售，或注册、注销通知、注销停止这类不同行动放进同一组，合并时会被日期/地点差异标成冲突，需要协调者拆分后重新合并。

主台账 `records.jsonl` 只保留每个 ID 的最新状态；分片文件保留完整追加历史。合并报告默认写到案例目录的 `merge-report.json`，写主台账前先校验整批记录，失败时不写半批。

## 冲突裁决

合并命令不做真伪判断。协调者按证据层级裁决：原件 > 原始报道 > 聚合与转载。能在同一时间窗对齐的合并；不能对齐的保留两种说法，写进 `date_note` 或分列。不能因为分片没找到，就删除另一个分片已有的来源。

## 交付

`delivery.json` 增加 `parallel` 段：

```json
{
  "parallel": {
    "workers": 3,
    "shards": [
      {"id": "s01-news", "family": "新闻与特稿", "stop_reason": "新检索只产生同源转载", "open_gaps": 4}
    ],
    "merge": {"report": "merge-report.json", "conflicts": 1, "deduped_events": 5, "corroborated_downgraded": 2}
  }
}
```

`check_delivery.py` 会校验 worker 数、分片停止原因、合并报告路径与统计计数。报告交付头写明并行模式、worker 数与分片数；附卷增加「分片覆盖表」，列出每个分片的范围、状态、停止原因与开放缺口。

## 质量红线

- worker 的证据标准与单线程完全相同：先打开再引用、逐页核读、失败如实记录；
- 分片内不得把同稿转载标成独立证实；跨分片是否独立由合并后重算；
- 分片记录必须能定位到 `raw/`；只有摘要的条目按原规则标 `search_only` 或 `metadata_only`；
- 协调者不能拿分片数量或并行速度冒充调查覆盖；
- 合并报告里的冲突与降级必须进入附卷或下一轮计划，不能留在 `merge-report.json` 里无人处理。
